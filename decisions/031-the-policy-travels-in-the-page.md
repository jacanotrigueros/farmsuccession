# 031 — The policy travels in the page, so an inline style is a build error

**2026-10-17.** Every built page carries a Content-Security-Policy in a `<meta>`
element. Astro hashes the `<style>` elements it generates, so the policy needs no
`'unsafe-inline'`. A hash cannot cover a `style="…"` attribute, so one appearing in a
built page is a failure rather than a thing to loosen the policy for.

## The question

"Nothing on this site comes from anywhere else" was a property of the build, checked by
reading the output. Should the browser be told the same thing, and if so, how strict
can the policy be before it costs more than it is worth?

A header is the usual answer and is not available here. A `<meta>` element is, but it
cannot carry `frame-ancestors`, and it is written into every one of 445 pages. Against
that, a policy with `'unsafe-inline'` in `style-src` permits most of what the policy
exists to refuse, which would make it decoration.

## What the evidence said

GitHub Pages sends no security headers of its own on a custom domain. The live response
for `https://farmsuccession.eu/` carries `Server: GitHub.com` and no
`Strict-Transport-Security`, `X-Content-Type-Options`, `Referrer-Policy` or
`Content-Security-Policy`. There is no configuration file for them, and a proxy in front
would put every reader's request through a third party — the thing the no-third-party
rule exists to prevent.

The built site needs very little allowed. Across `dist/`:

- no inline `<script>` except `application/ld+json`, which the HTML specification stops
  preparing before any policy check, so it is never affected;
- no `style="…"` attribute and no `on*` handler anywhere;
- every font, image, stylesheet and script is first-party;
- the only external origins in the output are hyperlink targets and `schema.org` inside
  JSON-LD, neither of which is fetched.

Two things do need naming. Pagefind compiles WebAssembly to search, which requires
`'wasm-unsafe-eval'` — that permits WebAssembly and nothing else, and is not
`'unsafe-eval'`. And twelve forms post to `mailto:contact@farmsuccession.eu`, which
`form-action 'self'` would block.

Reproduce it with:

```bash
curl -sSI https://farmsuccession.eu/ | grep -i 'security\|content-type-options\|referrer'
cd frontend && npm run build
grep -rho '<script[^>]*>' --include='*.html' dist | sort | uniq -c
grep -rl 'style="' --include='*.html' dist | wc -l
grep -rho 'url([^)]*)' dist/_astro/*.css | sort -u | head
```

The policy was then built and exercised rather than read: the search returns its results
with every filter counted, which proves the WebAssembly, the worker and the index
fetches all pass. The one violation a browser reported came from a page holding a single
paragraph and no code from this site, which is how it was identified as the preview
harness rather than the site.

## The decision

1. **Every page carries the policy in a `<meta>` element**, generated by Astro's
   `security.csp` so the hashes of its own `<style>` elements stay correct by
   construction.
2. **`'unsafe-inline'` and `'unsafe-eval'` are never added.** A test refuses both by
   name. If something needs one, the thing is fixed, not the policy.
3. **An inline `style="…"` attribute in a built page is a build error.** The hashes
   cover `<style>` elements; nothing can cover an attribute short of allowing every
   inline style. A test fails on the first one and says why.
4. **`'wasm-unsafe-eval'` is allowed and named**, because the search compiles
   WebAssembly, and `form-action` names the correction address.

## What it costs

`frame-ancestors` only exists as a header, so this does not protect against framing.
For a site with no session, no credential and no form carrying a reader's data, an
attacker gains nothing from framing it that they could not get by copying it.

The policy is repeated in all 445 pages, a few hundred bytes each, compressed away by
the time it reaches a reader.

The real cost is point 3, and it is worth stating plainly because it will be met before
anything else here: **Astro's Markdown code highlighting, Shiki, emits inline `style`
attributes on every token.** The build already warns about it. No page uses a code block
today, so nothing is broken; the day somebody writes one, the policy will blank the
highlighting rather than fail the build, which is exactly the kind of silent breakage
the test exists to turn into a loud one. The answer then is a highlighter that emits
classes — Astro's own suggestion is Prism — and not `'unsafe-inline'`.

## What would overturn it

Move this to a response header the day FarmSuccession is served by something that can
send one, and take `frame-ancestors` with it.

Loosen `style-src` only if a dependency the project genuinely needs cannot be made to
emit classes, and record what was tried before it was given up.
